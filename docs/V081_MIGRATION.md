# v0.8.1 — dry-run, shadow и восстановление лицензий

Статус: **read-only отчёт реализован**, автоматического преобразования legacy в новые права нет; ни одна реальная база не анализировалась. Последняя присланная сборка содержит схему и тестовые записи, но не содержит исторических лицензий или внешних свидетельств их условий.

## Соответствие данных

| Источник | Значение в v0.6 | Целевая модель | Решение |
|---|---|---|---|
| `licenses.id` | идентификатор старой записи | не равен автоматически `license_grants.id` | сохранить как исходное свидетельство; связь не выдумывать |
| `licenses.user_id` | ссылка на пользователя | `license_grants.user_id` | проверить наличие пользователя; это само по себе не доказывает условия |
| `licenses.key_hash` | исторический verifier, формат/происхождение не доказаны для всех данных | `license_grants.key_hash` | не переписывать, не повторно хешировать и не считать совпадение достаточным доказательством |
| `licenses.active`, `expires_at` | старый статус и срок | `activated_at`, `expires_at`, `revoked_at` grant | inactive/expired — недействительно; null/неверный срок — неоднозначно; не создавать новый grant |
| legacy platform, device limit, plan, activation, provenance | отсутствуют в `licenses` | snapshot в `license_entitlements`, точные grant/активация | неоднозначно, требуется внешнее доказательство и ручная сверка; никогда не подставлять текущие значения тарифа |
| `license_grants` + существующий валидный snapshot | данные и действующие условия уже записаны | те же grant и snapshot | однозначно **сохранены**, не вновь перенесены; проверка доступа по серверным правилам |
| grant без snapshot, владелец отсутствует или snapshot некорректен | недостаточно данных | fail-closed | неоднозначно; переоформление только после подтверждения условий |
| revoked, expired, disabled, not activated | недействующий/неактивный grant | те же данные | сохранить, без выдачи прав; blocked user не является доказательством недействительности самой лицензии |

`license_shadow.py` классифицирует каждую запись `licenses` и каждый grant; действие отчёта — `skipped` или `preserved`, записей **перенесено 0**, потому что безопасное автоматическое преобразование из доступной схемы не доказано. Отчёт не создаёт persistent quarantine, таблицу mapping или backfill. Он не выводит ключи, хеши или credentials, но содержит внутренние ID пользователей и потому требует ограниченного доступа.

## Dry-run и shadow

SQLite — изолированная копия известной базы с ревизией `f60e00000001` или `4dbfc4c29581`:

```sh
python scripts/license_shadow.py --sqlite /path/OLD-copy.db --output /secure/location/shadow-before.json
python scripts/migrate_v06_sqlite_copy.py /path/OLD-copy.db /path/NEW-copy.db
python scripts/license_shadow.py --sqlite /path/NEW-copy.db --output /secure/location/shadow-after.json
```

Для PostgreSQL переменную с URL установить безопасно в локальном окружении, не записывать в shell history; использовать отдельную копию и отдельную read-only роль:

```sh
python scripts/license_shadow.py --postgres-url-env SHADOW_DB_URL --output /secure/location/shadow.json
```

SQLite открывается `mode=ro` с `query_only`, PostgreSQL использует `REPEATABLE READ READ ONLY`. Вывод создаётся исключительно новым файлом (в POSIX mode 0600); существующий файл не перезаписывается. Используйте новый путь для каждого повторного запуска и сравнивайте поля, кроме времени. Дополнительные ограничения прав доступа и безопасное удаление отчётов — ответственность оператора. Схема проверяется на необходимые колонки и revision, а не побайтно на все исторические варианты; неизвестный revision отклоняется. Не считать отчёт автоматической миграцией.

Shadow сопоставляет сырой `active` **последней** legacy-лицензии, который показывала v0.6 account-сводка, с текущим результатом server-side grant/account и snapshot. Это сопоставление показателей, а не доказательство, что старая сводка реально авторизовала игровую операцию; конкретные устройства и платформы в нём не проверяются. Не сопоставлять записи по ID/hash без подтверждённой связи. При изменении данных после отчёта нужна новая проверка в согласованном окне; отчёт не разрешает cutover.

## Проверенная репетиция и что ещё нужно

Автотесты создали отдельные SQLite и PostgreSQL v0.6 базы с тестовыми лицензиями, сформировали read-only отчёт, сделали отдельную копию, запустили Alembic до v0.8 и сравнили классификации/shadow. Проверили неизменность исходника, повторный read-only scan и защиту от перезаписи отчёта. PostgreSQL копия создана через TEMPLATE; это не репетиция pg_dump/restore и не реальные данные. Отчёт каждого прогона временный, с тестовыми данными; журналы — в общем отчёте тестирования.

План cutover: остановить запись; подтвердить целостную резервную копию с отдельной проверкой восстановления; получить перечень всех потребителей; провести scan/shadow на копии и вручную разобрать каждую неоднозначность с доказательствами; согласовать безопасное переоформление через существующий административный процесс; повторить проверки и подготовить план окна. Не выполнять операцию автоматически, если неизвестны владелец, условия или происхождение ключа. Cutover не реализован и не отрепетирован на реальных данных.

Откат: до новых v2-записей — остановить сервисы и восстановить проверенную резервную копию в отдельную БД; проверить ревизию и данные до подключения. После начала v2-записей простое восстановление теряет новые записи: сохранить post-cutover журналы/копию, выполнить отдельный подтверждённый reconciliation/forward recovery и повторно сверить; общий автоматический replay не реализован. Alembic downgrade `4dbfc4c29581` намеренно запрещён. Этот план не является выполненной проверкой production restore.
