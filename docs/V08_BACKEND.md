# NØRI v0.8.0 — Backend v2 (development increment)

## Scope and status

Working locally on SQLite and PostgreSQL: server-created device UUID, short-lived pairing with explicit user confirmation, one-time claim, revocation, rate buckets, calculated device access, separate support/event/command persistence, queue leases and two-stage command acknowledgement. This increment is **not complete or production-ready**: a trusted game execution verifier does not exist, so `EXECUTED` is refused (503); neither game SDK is connected. The C++ host still denies every command and its pairing flow is not connected to the UI. Live Telegram was not tested. No payment functionality is invented.

## Model and source of truth

- Logical **License and Grant** are one `license_grants` row (ADR-002 compatibility mapping); a grant belongs to a `users` row. `license_entitlements` is the immutable plan platform/device-limit snapshot; `Device` is the existing `devices` row. `evaluate` in `app/v2/security.py` computes current access from account, grant, snapshot, device, and UTC time. No missing snapshot is inferred. It verifies account status, activated and not revoked, activation <= now < expiry, snapshot and platform; device checks its ownership, active status, credential verifier and active count <= limit. Pair confirm checks the same grant/account predicate and available pending/active slots under lock.
- Existing `licenses` rows remain untouched and are not an access authority; there is no automatic backfill or shadow/cutover. Historic grant records lacking snapshots **cannot** authorize: operators must reconcile and reissue from an approved plan, not invent entitlements. The `/v1/users/{telegram_id}` summary uses v2 evaluation; `/v1/.../licenses` keeps historical lifecycle `status` for compatibility and adds `access.allowed/reason`. Lifecycle `active` alone is not access. `GET /v2/licenses` calculates current access without a device.
- `/v2/device/access` calculates fresh per-request status, platform, expiry, device limit, available configured feature names and `last_checked_at`; it updates `devices.last_seen_at` on success. User and license come from server binding; no client-supplied user/grant/device identity is trusted for device operations. Feature names are a global operator allowlist, not per-plan feature entitlements; the latter remain unimplemented.
- `v2_pairings` stores code/claim SHA-256 verifiers, server-assigned UUID, expiration and transaction state. `devices.credential_hash` holds only verifier. `v2_rate_buckets` stores per-scope hashes and counters. `game_events` + `game_event_jobs` are separate from existing support `notification_jobs`; `remote_commands` is a third queue. No game data are fabricated by the application.

## Pairing and HTTP API

Base `/v2`; responses JSON; timestamps UTC, no-store. Protected operations use individual `Authorization: Bearer <user session>` minted by the trusted Telegram ingress or `<device credential>` as explicitly marked. All request models reject unknown fields. Rate buckets use 10-minute fixed windows and the direct peer IP (proxy headers are not trusted). Do not expose an HTTP server without TLS at the edge and a reviewed trusted-proxy/rate-limit deployment. Errors are FastAPI `{"detail":"..."}`, not the earlier planned error envelope; 422 is sanitized on v2. 401 means missing/invalid credential, 403 entitlement/ownership denied, 404 unavailable, 409 replay/conflict, 410 expired pairing, 422 invalid input, 429 limit with Retry-After, 503 feature/DB unavailable. API documentation is also generated by `/openapi.json` at runtime. There is no client-supplied device identifier on start.

| Method / path | Authorization | Request → success | Limit / semantics |
|---|---|---|---|
| POST `/device/pairings` | none | `{platform:"hassle_rp_2"\|"radmir_crmp",name}` → 201 `{pairing_id,device_id,pairing_code,claim_secret,expires_at}` | 10/IP/10 min. ID is server-generated; code is 16 Base32 chars, 300 s; secret 32 random bytes. No secret in URL. |
| POST `/pairings/preview` | user | `{pairing_code}` → `{pairing_id,device_id_suffix,platform,name,expires_at}` | 60/IP and 15/user/10 min; confirmation is separate. |
| POST `/pairings/confirm` | user | `{pairing_id,pairing_code,license_id}` → `{pairing_id,status:"confirmed",expires_at}` | 60/IP and 15/user; chosen grant must belong to user. Serializes reservations; repeat returns 409. |
| POST `/device/pairings/claim` | claim secret | `{pairing_id,claim_secret}` → `{device_id,device_credential,credential_type:"Bearer"}` | 60/IP and 10/pairing; one-time claim. Lost response: cancel/revoke, start again. |
| POST `/pairings/{id}/cancel` | confirming user | `{}` or no body → `{pairing_id,status:"cancelled"}` | Cancels reservation or revokes claimed device; repeat succeeds for owner. |
| POST `/devices/{id}/revoke` | device owner user | `{}` or no body → `{device_id,status:"revoked"}` | Revokes credential, owner only. Admin/owner can use protected v1 admin revoke subject to its RBAC. |
| GET `/licenses` | user | no body → `{licenses:[{license_id,allowed,reason,expires_at,platform,device_limit,checked_at}]}` | Grant/account predicate, not device access. |
| GET `/device/access` | device | no body → `{device_id,license_id,platform,status,expires_at,server_time,last_checked_at,device_limit,features}` | Each request rechecks; 1000/IP device-auth window. A response is not an offline capability. |
| POST `/events` | device | `{event_id,event_type,payload}` → 202 `{accepted,replayed,event_id}` | Device-scoped dedup and event/job atomic transaction; changed payload 409. Type must be explicitly enabled; otherwise 503. Payload <=4096 serialized bytes. |
| POST `/commands` | user | `{device_id,idempotency_key,command_type,payload,ttl_seconds}` → 201 `{command_id,status,expires_at,attempts,error_code,replayed}` | Owner + entitlement; key scoped to user; changed request 409; TTL 10–3600 s. Types disabled by default. |
| GET `/commands/{id}` | owner user | no body → current command status | Foreign ID 404; status transitions also updated lazily. |
| POST `/commands/{id}/cancel` | owner user | no body → `CANCELLED` | Only before ACK; after ACK 409. |
| POST `/device/commands/claim` | device | no body → `{command:null}` or command + `lease_token`, `lease_until` | Fresh entitlement each call; 30 s lease; at most 5 deliveries; 1/2/4/8 s retry delays after lease timeout. |
| POST `/device/commands/{id}/ack` | device | `{lease_token}` → `ACKNOWLEDGED` | Receipt only; same token repeated is idempotent. Never implies execution. |
| POST `/device/commands/{id}/authorize` | device | `{lease_token}` → `{authorized:true,checked_at,command_id,expires_at}` | Checks current entitlement, TTL, type and ACK; live response only. Not a signed offline permit; cannot stop a call already running. |
| POST `/device/commands/{id}/result` | device | `{lease_token,result:"FAILED"\|"EXECUTED"}` | FAILED stored; EXECUTED returns 503 until an approved platform verifier is implemented. |

PENDING expires before ACK; expired lease is eligible for retry after delay, unless TTL or retry limit was reached. ACKNOWLEDGED is never blindly redelivered; after 120 s without a result it becomes FAILED/EXECUTION_UNKNOWN during a later queue/status operation. Expiration/timeout is currently lazy: no standalone sweeper, so status can remain stale until accessed. The failure result is a device report, not verification of game behavior. Remote command payloads are generic JSON with a size cap and have no approved game schema; no types are enabled by default.

The event worker is independent of support: persistent event/job, lease, capped retries and metadata-only message; it checks user/device entitlement and opt-in (`notification_settings` platform/kind). Delivery is at-least-once, not exactly-once; lost confirmation may duplicate a Telegram notification. The v0.6 support worker is preserved and invokes the separate event worker. Event `payload` is stored in the DB in plaintext; schema, encryption, retention, deletion, PII policy, platform-specific approval and live delivery tests are pending. Do not enable event types for production until these are resolved.

## Configuration and deployment

Existing variables in `.env.example` still apply. `V2_APPROVED_EVENT_TYPES` and `V2_APPROVED_COMMAND_TYPES` default to empty strings (all game-dependent types disabled). Comma-separated values are an operator control, not proof an SDK permits a feature. For isolated tests only, fixtures set synthetic types. `AUTO_CREATE_SCHEMA=false` and Alembic are required in deployed environments. v1 experimental pairing and v1 `/device/me` now return 503 regardless of `DEVICE_PAIRING_ENABLED`: they were disabled because they used fallback permissions without a snapshot and lacked v2 controls. Existing v1 user/admin/support APIs remain, but direct old grants lacking plan snapshot no longer provide v2 access. v0.7 pre-v2 `device_id` in start request is rejected; updated v0.8 Core sends only platform/name. The changed Core protocol has not completed end-to-end authentication with DPAPI.

Rate limiting is database-backed and shared across workers using the same DB; it is not a substitute for an edge/WAF, an unauthenticated flood can consume DB capacity, proxy IPs need explicit trusted deployment design, and expired buckets require an operational retention/cleanup job. Legacy v1 endpoints do not have comprehensive rate limits. No production load, penetration or independent security audit has been completed. Disable request/body/SQL-parameter logging in the reverse proxy and application; DB engine hides SQLAlchemy parameters, and v2 validation errors are sanitized, but complete infrastructure logging/redaction has not been verified. Run TLS at a trusted proxy; local HTTP test is loopback only.
